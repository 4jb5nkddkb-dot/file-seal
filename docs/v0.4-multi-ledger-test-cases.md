# v0.4 多账本迁移与并发专项测试用例

关联任务：[#4](https://github.com/4jb5nkddkb-dot/file-seal/issues/4)
关联开发线：`feat/v0.4-multi-ledger`

本文件定义 v0.4 在进入 Ready for Review 前必须执行的专项测试。测试应优先使用临时目录和临时进程，不得修改用户真实账本。每项测试都要记录稳定退出码、错误类别、账本 hash 或报告文件作为证据。

## 测试约定

### 测试对象

- `L0`：新建空账本；
- `L1`：包含 3 条有效旧格式记录的 v0.2.x JSONL 账本；
- `L2`：包含 3 条有效哈希链记录的 v0.3.x 账本；
- `F`：待封印文件；
- `T`：迁移目标路径；
- `R`：迁移报告；
- `K`：并发写入进程数，默认 8；
- `N`：每个进程追加记录数，默认 25。

所有测试开始前记录：运行平台、Rust 版本、提交 SHA、临时目录路径、测试命令和 ledger schema version。

### 通用安全不变量

1. 任意失败都不能覆盖原账本。
2. 任何正式账本都不能出现半条 JSON、重复序号或不可验证链尾。
3. 账本外的路径不能因账本名称或迁移参数被写入。
4. 同一账本的有效记录序号必须严格连续；不同账本之间不共享序号。
5. 锁、临时文件和异常退出不会导致永久死锁或静默数据丢失。

## A. 迁移测试

### MIG-001 有效旧账本的非破坏性迁移

**前置条件**：创建 `L1`，保存原始字节和 SHA-256。

**操作**：执行 `ledger migrate L1 --to T`，读取目标账本并运行完整链验证。

**预期**：命令成功；原始字节和 SHA-256 不变；`T` 可独立验证；记录数量保持一致；报告包含 source hash、target ledger ID、migration timestamp 和 schema version。

### MIG-002 迁移信任边界

**前置条件**：准备内容正确但没有历史哈希链证明的 `L1`。

**操作**：迁移后修改一条新链记录并验证；读取迁移报告。

**预期**：修改被检测；报告明确写出“可信起点为迁移时刻”，不能声称证明迁移前历史未被篡改。

### MIG-003 损坏 JSON 行

**前置条件**：复制 `L1`，在第 2 行写入截断 JSON。

**操作**：执行迁移。

**预期**：失败并返回稳定的 `ledger-parse`/行号错误；`L1` 不变；`T` 不存在或不包含可被识别为正式账本的半成品。

### MIG-004 重复或跳跃序号

**前置条件**：构造序号 `0, 0, 2` 或 `0, 2, 3` 的输入。

**操作**：执行迁移和验证。

**预期**：迁移拒绝输入；不得自动排序、补号或静默丢弃记录。

### MIG-005 非法哈希字段

**前置条件**：使用错误长度、非十六进制或大小写不符合规范的 SHA-256 字段。

**操作**：执行迁移。

**预期**：按 schema 错误失败；不得把非法字段当作普通字符串继续签入新链。

### MIG-006 目标路径安全

**前置条件**：目标名依次设为 `../escape`、绝对路径、包含 NUL 的名称、空字符串和超长名称。

**操作**：执行迁移。

**预期**：全部拒绝；仓库根目录外没有新文件；原账本不受影响。

### MIG-007 目标已存在

**前置条件**：先创建有效目标账本 `T`，再重复执行同一迁移。

**操作**：再次执行迁移，不提供覆盖确认。

**预期**：返回 already-exists/conflict；`T` 字节不变；不追加重复记录。

### MIG-008 迁移幂等性

**前置条件**：对同一只读输入执行两次迁移到两个不同目标 `T1`、`T2`。

**操作**：比较两个目标的规范化记录、源摘要和验证结果。

**预期**：除明确允许的迁移时间和随机 ledger ID 外，内容一致；两次执行不会修改源。

### MIG-009 写入故障回滚

**前置条件**：通过可注入的测试文件系统或模拟写满磁盘，在写入目标中途制造失败。

**操作**：执行迁移。

**预期**：源账本可验证；目标不会被误认为完成；临时文件带有明确临时后缀或被清理；下次迁移可重新开始。

### MIG-010 迁移后跨账本隔离

**前置条件**：迁移得到 `T`，另建空账本 `L0`。

**操作**：在 `T` 验证迁移记录，在 `L0` 验证同一路径。

**预期**：`T` 返回记录，`L0` 返回 `NoSeal`；任何一方链尾变化不影响另一方。

### MIG-011 迁移与备份恢复

**前置条件**：复制 `L1` 的备份，完成迁移，再恢复原备份到新路径。

**操作**：分别验证源备份和目标账本。

**预期**：两个对象都能被识别为不同信任起点；恢复不会覆盖目标或改变目标链尾。

### MIG-012 报告完整性

**前置条件**：完成一次成功迁移。

**操作**：修改报告中的 source hash、target tip 或时间字段后再次读取报告。

**预期**：报告校验失败，或报告明确是非可信导出；不得把被修改的报告当作当前验证结果。

## B. 同一账本并发写入

### CON-001 多进程追加的序号唯一性

**前置条件**：创建空账本 `L0`，启动 K 个进程，每个追加 N 条不同备注。

**操作**：使用 barrier 同时开始；等待所有进程退出。

**预期**：若策略是串行化，K×N 条全部成功；若策略允许冲突重试，最终有效记录数量仍为 K×N。序号恰为 `0..K*N-1`，无重复、空洞或交叉 JSON。

### CON-002 冲突检测与重试

**前置条件**：两个进程读取同一链尾后延迟写入。

**操作**：让进程 A 和 B 同时尝试追加。

**预期**：一个成功；另一个得到可分类的 conflict 并按协议重读链尾重试，或明确失败。禁止两个进程都写出同一序号。

### CON-003 强制终止持锁进程

**前置条件**：进程 A 在持锁期间暂停，记录锁文件/文件锁状态。

**操作**：SIGKILL/等价终止 A，随后启动进程 B 写入。

**预期**：B 最终可以获得锁或得到明确恢复提示；不会永久死锁；账本仍是可验证 JSONL。

### CON-004 写入中断和尾部截断

**前置条件**：在 append 写入 JSON 行的一半时终止进程。

**操作**：重新打开账本并执行验证，再执行一次追加。

**预期**：验证明确报告 truncated-tail，或由原子写入保证账本完全不受影响；不得跳过损坏尾行继续追加。

### CON-005 高竞争压力

**前置条件**：K=16、N=100，重复运行至少 10 轮。

**操作**：统计成功数、冲突数、重试数、失败数和每轮链尾。

**预期**：每轮无数据竞争；最终链尾可重算；失败只属于明确的资源/冲突错误；不存在偶发序号断裂。

### CON-006 同一文件多次并发封印

**前置条件**：多个进程对相同文件并发执行 seal。

**操作**：并发写入相同 `path`、相同文件 hash。

**预期**：记录数和策略一致（允许重复审计记录或去重，但必须有文档说明）；每条记录链有效；不会出现不同 size/hash 的伪冲突。

## C. 不同账本并发写入

### CON-007 不同账本无锁互相阻塞

**前置条件**：创建 `work` 和 `personal` 两个空账本。

**操作**：分别启动 K 个进程写入两个账本。

**预期**：两个账本可以并行推进；一个账本的锁和冲突不会污染另一个账本；各自序号从 0 开始连续。

### CON-008 同一路径跨账本验证

**前置条件**：同一个文件在两个账本中并发封印。

**操作**：完成后分别读取两个账本。

**预期**：两个账本拥有不同 ledger ID 和独立链尾；删除其中一个账本记录不会影响另一个。

## D. 迁移与并发竞态

### RACE-001 迁移期间追加旧账本

**前置条件**：对大 `L1` 开始迁移，在读取源和提交目标之间暂停迁移。

**操作**：尝试向源账本追加，再让迁移继续。

**预期**：实现必须选择并记录一种策略：迁移持锁阻止追加，或检测源链尾变化并重新开始；不能生成缺失中间记录的目标。

### RACE-002 两个迁移者竞争同一目标

**前置条件**：两个进程同时把同一 `L1` 迁移到同名目标。

**操作**：同时提交目标。

**预期**：只有一个完整目标成功；另一个得到 conflict/already-exists；目标可验证，不能出现交错内容。

### RACE-003 迁移和新账本写入隔离

**前置条件**：迁移 `L1` 到 `T`，同时向已存在的 `work` 账本追加。

**操作**：并发运行并等待结束。

**预期**：`work` 不被迁移锁阻塞到超时；`T` 仍完整；两个账本的日志和错误互不混淆。

## E. 测试实现建议

- Rust 单元测试：名称包含 `multi_ledger_migration`、`concurrent_append` 或 `migration_race`，使用 `tempfile::TempDir`。
- 进程级并发测试：使用 `std::process::Command` 启动 CLI，使用临时 barrier 文件或管道同步，不依赖 sleep 作为唯一同步手段。
- 故障注入：为写入器抽象文件系统或注入 `before_commit`/`after_lock` 钩子，避免用真实磁盘写满作为唯一测试。
- 平台矩阵：至少 Linux 和 Windows；锁、rename、删除打开文件和路径规范化行为必须分别验证。
- CI：普通 PR 运行确定性测试；压力测试和故障注入可放入 nightly 或手动 workflow，但发布前必须有最近一次成功记录。

## 通过门槛

v0.4 不能因为只通过正常路径而发布。MIG-001 至 MIG-012、CON-001 至 CON-008、RACE-001 至 RACE-003 必须有结果；任何 panic、静默丢记录、永久死锁、源账本被覆盖或失败开放都阻止合并。
